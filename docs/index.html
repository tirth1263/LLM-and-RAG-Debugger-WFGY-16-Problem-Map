This debugger routes a messy bug report to exactly one of 16 reproducible failure modes from the WFGY Problem Map, tells you which document to open first, and gives you a patch you can apply at the prompt layer without touching your infrastructure.

01 The debugger

Paste a trace, a log, or a prompt / answer pair. Describe it the way you would in a team channel — symptom first, no diagnosis.

Your key never leaves this browser tab. This page is static — there is no backend to send it to. The request goes straight from your browser to the endpoint you typed, and the key is held in memory only (never written to storage). Because it is a direct browser call, the endpoint must send CORS headers; if it does not, use the offline engine or the route and paste it into any chat model.

03 How it works

A diagnostic layer in front of your app. Nothing in your stack changes.

1

You paste the mess

Prompt, answer, retrieval trace, stack log. Symptom-first, exactly as it landed in your channel.

2

References load

The CLI pulls TXTOS.txt and ProblemMap/README.md straight from the upstream WFGY repo, so the taxonomy is never a stale copy.

3

The firewall reasons

A semantic-firewall system prompt forces diagnosis before prescription: quote the evidence, then pick the number.

4

You get a number

One primary No.X, an optional secondary No.Y, a confidence level, the doc to open first, and a three-step patch.

Two engines, same map

The offline engine is a transparent weighted-signal classifier that runs entirely in your browser. It shows you every phrase it matched and what that phrase scored, so you can argue with it. It is deterministic and needs no key — ideal for a first pass and for demoing the taxonomy.

The live engine sends the same structured prompt to any OpenAI compatible endpoint. It reads nuance the keyword scorer cannot, and it writes the patch steps in the vocabulary of your specific bug. Use it when the offline result is low confidence or the top two modes are close.

Why a fixed taxonomy beats free-form advice

"Try improving your chunking" is not a fix, it is a mood. A number is falsifiable: it names the layer that broke, predicts what you should see in the trace, and points at one document. If the number is wrong the trace will say so, and you will have learned something either way.

It also gives a team shared vocabulary. "That's a No.2, not a No.1 — retrieval was fine" ends an argument that would otherwise cost an afternoon.

04 Quickstart

Python 3.9+, two dependencies, one file. Works as a CLI or as a single notebook cell.

Terminal
git clone https://github.com/tirth1263/LLM-and-RAG-Debugger-WFGY-16-Problem-Map.git
cd LLM-and-RAG-Debugger-WFGY-16-Problem-Map

python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install -r requirements.txt
python main.py
Nebius Token Factory
# Nebius Token Factory
NEBIUS_API_KEY="your_nebius_api_key"

# The script reads OPENAI_API_KEY, so export the same value here
OPENAI_API_KEY="$NEBIUS_API_KEY"

# Nebius OpenAI compatible endpoint
OPENAI_BASE_URL="https://api.tokenfactory.nebius.com/v1/"

# Any Nebius model id
OPENAI_MODEL="meta-llama/Meta-Llama-3.1-70B-Instruct"

Every variable is optional. Skip them all and the script asks for the key with getpass, then for the base URL and model id, at runtime. For Colab, Jupyter or a Nebius notebook, paste the whole of main.py into one cell and run it.
